This is my one-stop note for getting concurrent work done in Python. It walks from the GIL up through threads, processes, and `asyncio`, and it covers every coordination primitive along with the patterns and pitfalls that actually show up in real code and in interviews. Each idea comes with a plain analogy, runnable code, and the gotcha that tends to bite people.

If you remember only one thing, make it this: before you pick a tool, ask whether your program spends most of its time **waiting** (network, disk, a database) or **computing** (loops, parsing, math in Python). Waiting points you toward `asyncio` or threads. Computing points you toward processes. Almost everything else in this note is a consequence of that one split, and the reason the split exists at all is the GIL.

# Getting the mental model

## The restaurant analogy

The four ways of doing work map nicely onto a restaurant.

1. **Synchronous (ordinary Python).** One waiter takes an order, walks to the kitchen, and stands there until the food is ready. Nothing else happens while they wait.
2. **Multithreading.** You hire ten waiters who share one kitchen. They take turns at the stove, because only one of them can actually cook Python at a time, but while one waits for the oven another can keep busy. This works really well when there is a lot of waiting involved.
3. **Asyncio.** You have one very efficient waiter. They take an order, hand it to the kitchen, and immediately move on to the next table. When a kitchen bell rings, meaning some I/O has finished, they pop back to that table to continue. One person, almost never standing idle.
4. **Multiprocessing.** You build ten separate restaurants, each with its own kitchen and staff. Now you really can cook ten dishes at once, but the restaurants cannot share ingredients directly. Anything one sends to another has to be boxed up and shipped, which in Python means it gets pickled.

## Processes vs threads vs asyncio at a glance

| Feature | Multiprocessing | Multithreading | Asyncio |
| --- | --- | --- | --- |
| Unit of work | OS processes | OS threads | Coroutines on one thread |
| Memory | Separate per process | Shared within the process | Shared, very low overhead |
| Who switches tasks? | The OS, preemptively | The OS, preemptively | The event loop, cooperatively |
| Runs Python in parallel? | Yes, on real cores | No, the GIL serializes bytecode | No, single thread |
| Cost of a switch | High, a whole new process | Medium, a thread | Tiny, closer to a function call |
| Best for | CPU-bound Python | Blocking I/O with sync libraries | High-volume async I/O |
| Sharing data | IPC and pickling | Direct, but you need locks | Direct, with care around awaits |
| Blast radius of a crash | Isolated to one process | Shared, can corrupt state | Shared |

The deepest difference in that table is **preemptive versus cooperative**. The OS can pause a thread anywhere, even in the middle of a single statement, which is exactly why shared data between threads needs locks. Asyncio only ever switches tasks at an `await`, so you always know the precise points where another task could sneak in.

## The GIL, the thing worth actually understanding

CPython keeps its own internals consistent (reference counts, object memory) with a single global lock. The rule it enforces is simple: only one thread runs Python bytecode at any given moment. That lock is the Global Interpreter Lock, or GIL.

A few things follow from it, and they explain most of what feels surprising about Python concurrency.

- **Threads do not speed up pure-Python CPU work.** Four threads adding numbers in a Python loop are no faster than one, because they just take turns holding the GIL.
- **Threads still help a lot with I/O.** When a thread blocks on a socket, a file read, or `time.sleep`, it releases the GIL so other threads can run. Many C extensions do the same, releasing the GIL around heavy native work. That covers a lot of NumPy math, hashing, compression, and database drivers.
- **Even a single thread can be paused between any two bytecodes.** The interpreter forces a check roughly every 5 milliseconds (you can read it with `sys.getswitchinterval()`), and also whenever a thread blocks.

Why does Python carry the GIL around? Because it makes memory management simple and fast for the common single-threaded case, and it keeps C extensions easy to write. The price you pay is that plain Python code does not get free use of multiple cores.

There is a real shift underway here. **Free-threaded Python**, introduced experimentally in 3.13 under PEP 703, can run without the GIL and give genuine multi-core parallelism for Python code. You can check whether it is active:

```python
import sys
print(sys._is_gil_enabled())   # False on a free-threaded build with the GIL turned off
```

It is opt-in today and still settling in, since some C extensions need updating, but it is clearly the long-term direction. Until it becomes the default, the safe assumption is that the GIL is present, which means you should reach for **processes** whenever you need parallel Python compute.

## CPU-bound vs I/O-bound, and how to tell them apart

This is the classification that decides everything else.

| Kind of work | What it spends time on | Reach for |
| --- | --- | --- |
| **I/O-bound** | Waiting on the network, disk, a database, a subprocess | `asyncio` with async libraries, or threads for blocking libraries |
| **CPU-bound** in pure Python | Computing, so loops, parsing, math written in Python | `multiprocessing` or `ProcessPoolExecutor` |
| **CPU-bound** but inside native code that releases the GIL | Heavy NumPy or C-extension math | Either threads or processes work |

To tell which one you have, look at where the time actually goes. If your function mostly sits inside `requests.get`, `open().read`, `cursor.execute`, or an `await`, it is I/O-bound. If it mostly grinds through `for` loops, string and JSON work, or math in plain Python, it is CPU-bound. When you genuinely cannot tell, profile it rather than guessing.

A good rule of thumb: `asyncio` is at its best when you spend most of your time awaiting I/O. If a function would block the thread for milliseconds or more without ever hitting an `await`, keep it off the event loop and offload it, which the asyncio section explains.

## A quick way to choose

```text
Is the work mostly WAITING or COMPUTING?

  WAITING (I/O-bound)
     |
     |-- Using async libraries (aiohttp, asyncpg, httpx)?  --> asyncio
     |-- Stuck with blocking libraries (requests, an ORM)? --> threads / ThreadPoolExecutor
     |
  COMPUTING (CPU-bound)
     |
     |-- Pure Python number or text crunching?  --> multiprocessing / ProcessPoolExecutor
     |-- Already in NumPy or C that frees the GIL? --> threads are fine too
```

The rest of the note takes the three toolkits one at a time, then covers the primitives and patterns that span all of them.

# Threads

Threads share memory inside a single process. They are cheap to start and great for overlapping work that spends its time blocked on I/O. The catch is that the shared memory comes with a responsibility: you have to coordinate access to anything more than one thread can touch.

## Creating threads with `threading`

```python
import threading, time

def download(name: str) -> None:
    print(f"start {name}")
    time.sleep(1)          # stands in for a blocking I/O wait, which releases the GIL
    print(f"done {name}")

threads = [threading.Thread(target=download, args=(f"file{i}",)) for i in range(3)]
for t in threads:
    t.start()              # starts running on a new OS thread
for t in threads:
    t.join()               # waits for that thread to finish
# All three sleeps overlap, so this takes about 1 second rather than 3.
```

A few things to know. `target` is the function to run and `args` are its arguments. `.start()` launches it on a new OS thread, and `.join()` blocks the caller until it finishes. There are also **daemon threads** (`Thread(..., daemon=True)`), which are background threads the program will not wait for. They get killed when the main program exits, so use them for something like a heartbeat logger, never for work that has to complete.

## Thread pools with `concurrent.futures`

Managing threads by hand gets tedious and error-prone. Most of the time you want the high-level pool, which handles creating threads, reusing them, and collecting results for you.

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time

def work(n: int) -> int:
    time.sleep(0.01)
    return n * n

with ThreadPoolExecutor(max_workers=4) as ex:
    # map keeps the input order, like a parallel version of map()
    print(list(ex.map(work, range(5))))           # [0, 1, 4, 9, 16]

    # submit plus as_completed lets you handle results the moment they arrive
    futures = [ex.submit(work, i) for i in range(5)]
    for fut in as_completed(futures):
        print(fut.result())                       # comes back in completion order
```

`submit(fn, *args)` hands you a **Future** right away, and you read the outcome later with `.result()`, which blocks, or check `.exception()`. `map(fn, iterable)` is the easy path when you just want all the results in input order, and any exception re-raises when you read that result. `as_completed(futures)` is what you want when results trickle in and you would like to react to each one as it finishes, for example to show progress. Leaving the `with` block calls `shutdown(wait=True)`, so it will not return until everything is done.

## Race conditions, and why shared state is dangerous

A line like `counter += 1` looks like one indivisible step, but it is not. It compiles down to four separate bytecodes:

```python
import dis
def f():
    global counter
    counter += 1
dis.dis(f)
#   LOAD_GLOBAL   counter   <- read the current value
#   LOAD_CONST    1
#   BINARY_OP     +=        <- add
#   STORE_GLOBAL  counter   <- write the new value back
```

If the OS pauses a thread in the gap between the **read** and the **write**, another thread can read the same old value, do its own increment, and write back. When the first thread resumes and writes, one of the two increments is silently lost.

```python
import threading

counter = 0
def bump():
    global counter
    for _ in range(100_000):
        counter += 1

threads = [threading.Thread(target=bump) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)   # may be less than 400000, because some updates get lost
```

Whether the loss actually shows up depends on timing and on the Python build, and that is exactly what makes these bugs so unpleasant. The code passes in testing and then fails in production under load. The lesson is to stop reasoning about whether a given operation happens to be atomic, and instead protect any shared mutable state with a lock.

It is worth knowing that a handful of single-bytecode operations, such as `list.append` or assigning `dict[key] = value`, do happen to be atomic in CPython today. You should not lean on that, though. It is an implementation detail of CPython rather than a language guarantee, and any read-modify-write like `+=` is never atomic.

## Synchronization primitives in `threading`

### Lock

A lock is the one-person bathroom. Only a single thread can hold it at a time, and anyone else who tries to acquire it waits until it is free.

```python
lock = threading.Lock()
with lock:                 # acquire here, release automatically on the way out
    counter += 1           # only one thread is ever inside this block
```

Always prefer the `with` form, because it releases the lock even if the code inside raises.

### RLock

A plain `Lock` will deadlock if the same thread tries to acquire it twice, which happens more often than you would think when one method that holds the lock calls another method that also wants it. A reentrant lock, `RLock`, lets the owning thread re-acquire it and just counts how many times.

```python
rlock = threading.RLock()
def outer():
    with rlock:
        inner()            # this would deadlock with a plain Lock
def inner():
    with rlock:            # same thread re-acquiring is fine here
        ...
```

### Semaphore

A lock lets exactly one thread through. A semaphore is the same idea with a counter, so you can let, say, five through at once. The classic use is capping how many requests you fire at an external service.

```python
sem = threading.Semaphore(5)     # at most 5 at a time
def fetch(url):
    with sem:
        ...                       # only 5 threads run this block at once
```

### Event

An event is a flag one thread flips while others wait for it. It is handy for a "config is loaded, you can start now" kind of signal.

```python
ready = threading.Event()
def worker():
    ready.wait()                  # blocks until someone calls set()
    print("go")
# elsewhere:
ready.set()                       # wakes every waiter at once
```

### Condition

A condition is a lock paired with a notification channel, which is what you want for producer and consumer style coordination where a consumer needs to wait until some shared state is ready.

```python
cond = threading.Condition()
items = []
def consumer():
    with cond:
        cond.wait_for(lambda: len(items) > 0)   # releases the lock while it waits
        item = items.pop()
def producer():
    with cond:
        items.append(42)
        cond.notify()                            # wake one waiting consumer
```

### Barrier

A barrier is a meeting point. Every thread waits at it until the agreed number have arrived, and then they all continue together.

```python
barrier = threading.Barrier(3)    # all 3 threads wait here, then go on together
def phase():
    do_part_one()
    barrier.wait()                # nobody passes until all three arrive
    do_part_two()                 # part two starts only after everyone finished part one
```

## Passing data with `queue.Queue`

Honestly, the cleanest way to share work between threads is not to share raw variables at all, but to pass data through a queue. `queue.Queue` does its own locking internally, so you get safe handoff without writing a single `Lock` yourself. This is the producer and consumer pattern.

```python
import threading, queue

q = queue.Queue(maxsize=10)       # maxsize gives you backpressure

def producer():
    for i in range(5):
        q.put(i)                  # blocks if the queue is full
    q.put(None)                   # a sentinel meaning "no more work"

def consumer():
    while True:
        item = q.get()            # blocks if the queue is empty
        if item is None:
            break
        print("processed", item * 10)
        q.task_done()

p = threading.Thread(target=producer)
c = threading.Thread(target=consumer)
p.start(); c.start(); p.join(); c.join()
```

There are two useful variants. `LifoQueue` behaves like a stack, and `PriorityQueue` hands out the lowest item first. Whenever you find yourself passing data between threads, prefer a queue over hand-rolled locks.

## Deadlock, livelock, and starvation

These are the three classic ways concurrent code goes wrong, and they are worth recognizing by name.

A **deadlock** is when two threads each hold a lock the other one needs, so both wait forever.

```python
# Thread 1: with A:  with B: ...
# Thread 2: with B:  with A: ...   the crossed order is the deadlock
```

The usual fixes are to always acquire locks in the same global order, to use `acquire(timeout=...)` so a thread gives up rather than waiting forever, or to avoid holding more than one lock at a time.

A **livelock** is subtler. The threads keep responding to each other and changing state, but never make real progress, like two people in a hallway who keep politely stepping the same way to let each other pass.

**Starvation** is when one thread never gets its turn, because others keep winning the contended lock or the scheduler keeps favoring them.

The best defense against all three is to keep shared mutable state to a minimum. Pass data through queues, keep the code inside a lock as small as you can, and never hold a lock while you do I/O.

# Processes

When the work is CPU-bound Python, threads cannot help you, because of the GIL. Separate processes are the answer. Each one gets its own interpreter and its own GIL, so they genuinely run on different cores at the same time. The cost is that they do not share memory, so any data that crosses between them has to be pickled.

## Process pools with `ProcessPoolExecutor`

The nice thing here is that the high-level pool mirrors `ThreadPoolExecutor` almost exactly, so moving CPU work from threads to processes is often a one-word change.

```python
from concurrent.futures import ProcessPoolExecutor
import math

def is_prime(n: int) -> bool:
    if n < 2:
        return False
    for i in range(2, math.isqrt(n) + 1):
        if n % i == 0:
            return False
    return True

if __name__ == "__main__":                       # this guard is required, see start methods
    nums = [112272535095293, 112582705942171, 15]
    with ProcessPoolExecutor() as ex:            # defaults to os.cpu_count() workers
        print(list(ex.map(is_prime, nums)))      # [True, True, False], spread across cores
```

This version really does use all your cores. The exact same loop under `ThreadPoolExecutor` would be no faster than running it on one thread, because the prime check is pure Python compute.

## Using `multiprocessing` directly

If you want lower-level control, the `multiprocessing` module gives you `Process` and `Pool`.

```python
from multiprocessing import Process, Pool

def task(n):
    return n * n

if __name__ == "__main__":
    # a single one-off process
    p = Process(target=task, args=(10,))
    p.start(); p.join()

    # a pool of workers
    with Pool(processes=4) as pool:
        print(pool.map(task, range(5)))          # [0, 1, 4, 9, 16]
        # imap and imap_unordered stream results, apply_async runs a single call
```

## Sharing data between processes

Since memory is not shared, you need an explicit channel whenever processes have to exchange data.

| Tool | What it is for |
| --- | --- |
| `multiprocessing.Queue` | Streaming items between processes, the producer and consumer pattern across cores |
| `Pipe` | A fast two-ended channel between exactly two processes |
| `Value` and `Array` | A handful of shared numbers in shared memory, guarded by a lock |
| `shared_memory.SharedMemory` | Zero-copy sharing of large buffers like NumPy arrays, available since 3.8 |
| `Manager` | A server process that hosts shared `list`, `dict`, and similar, convenient but slower |

```python
from multiprocessing import Process, Queue

def worker(q):
    q.put("result from child")

if __name__ == "__main__":
    q = Queue()
    p = Process(target=worker, args=(q,))
    p.start()
    print(q.get())                                # "result from child"
    p.join()
```

## Start methods and pickling

How a child process comes into being differs by platform, and it is worth understanding because it explains a common footgun.

With **fork**, which was the historical default on Linux, the child is a clone of the parent's memory. That is fast, but the child inherits locks and threads in whatever state they were in, which can be risky.

With **spawn**, which is the default on Windows and on macOS since 3.8, Python starts a fresh interpreter and imports your module again. That re-import is the reason you need the `if __name__ == "__main__":` guard. Without it, every child would re-run your top-level code, which would spawn more children, and you would get an endless cascade of processes.

There is also **forkserver**, a middle ground that forks each worker from a clean server process.

```python
import multiprocessing as mp
mp.set_start_method("spawn")    # set this once, early, inside the main guard
```

One more rule that trips people up: everything you send to a process, meaning the arguments, the return values, and the worker function itself, has to be picklable. That rules out lambdas, locally defined or nested functions, open file handles, and most lock objects. Define your worker functions at the top level of a module. Pickling also has a cost, so for very small tasks the overhead of starting a process and serializing data can outweigh the gain. Batch work into chunks with `chunksize=` when that happens.

# Asyncio

Asyncio gives you one thread running a single event loop that juggles thousands of overlapping I/O operations. It is cooperative, which means tasks run until they hit an `await` and then voluntarily hand control back. Because only one task runs at a time, you do not need locks around pure CPU sections, but you still have to think about coordination around those `await` points.

## Syntax and the entry point

`async def` defines a coroutine function. Calling it returns a coroutine object and does not actually run anything yet. `await` is where you hand control back to the loop until the thing you awaited is done. `asyncio.run(coro)` creates a loop, runs the coroutine to completion, and shuts the loop down. You use it once, at the top level of your program. Never nest `asyncio.run()` calls, and inside async code use `await` instead.

```python
import asyncio

async def main() -> None:
    await asyncio.sleep(0.1)
    print("done")

asyncio.run(main())
```

When you need the loop from inside async code, use `asyncio.get_running_loop()`. Steer clear of the older `get_event_loop()` patterns unless you are maintaining old code.

## The event loop

Think of the event loop as the conductor. It decides what runs when, and it handles pausing and resuming. It keeps spinning around two questions: did any background I/O finish since I last looked, and what is ready to run right now?

It works in three phases. First there is the **ready queue**, the coroutines that are ready to run Python right now, which the loop runs one at a time. Then comes **execution**, where the loop runs a task until it yields, which usually happens at an `await`. Finally there is the **I/O watcher**, the selector. When a task awaits a network call, the loop parks it and asks the OS to watch that socket. When the data arrives, the task goes back onto the ready queue.

## Blocking sleep vs cooperative sleep

Never call `time.sleep()` inside asyncio code, because it freezes the entire loop. Use the cooperative version instead.

```python
await asyncio.sleep(seconds)
```

That only pauses the current task and lets the others keep running. There is also `await asyncio.sleep(0)`, which is a polite way to say "yield so other tasks get a turn" without waiting on any timer.

## Offloading blocking work

Libraries that are not async, like blocking sockets, `requests`, a heavy `subprocess`, or some ORMs, will stall the whole loop if you call them inside a coroutine. You have two ways to push them off the loop.

The first is `await asyncio.to_thread(func, *args)`, available since 3.9, which runs a blocking callable in a thread pool. That is the right choice for blocking I/O, since I/O releases the GIL. The second is `loop.run_in_executor(executor, func, *args)`, the same idea but more explicit. Pass `None` for the default thread pool, or pass a `ProcessPoolExecutor` for CPU-heavy Python you cannot rewrite as async.

The important point is that CPU-heavy Python belongs in processes, not on the asyncio thread pool, otherwise you will just serialize on the GIL again.

## Coroutines on their own are sequential

A coroutine driven by the loop moves through a few states. It is **created** when you call it, at which point nothing has run yet. Then it is **scheduled** onto the ready queue, then **running** as the loop executes its body, then **suspended** when it hits an `await`, then **resumed** when the awaited thing is ready, and finally **done** when it returns.

The key insight is that awaiting one coroutine at a time, in a single flow, is sequential. You wait for each one to finish before the next starts. To get real overlap, you need tasks.

## Tasks give you overlap

Writing `await my_coro()` means run this coroutine all the way to completion before the next line in the current coroutine. To overlap work, you wrap it in a **task**, which the loop is free to interleave with others.

```python
t = asyncio.create_task(my_coro())   # scheduled right away, runs concurrently
# ... do other awaits in the meantime ...
await t                               # collect its result when you need it
```

| Action | What you write | What Python does |
| --- | --- | --- |
| Call a coroutine | `my_func()` | Creates a coroutine object and does not run it |
| Await a coroutine | `await my_func()` | Runs it now and pauses here until it finishes |
| Create a task | `asyncio.create_task(my_func())` | Schedules it so you can keep going |

## Running many at once with `asyncio.gather`

```python
results = await asyncio.gather(fetch(a), fetch(b), fetch(c))
```

`gather` wraps your coroutines in tasks, runs them concurrently, and gives you the results back in input order once they all finish.

There is one caveat worth internalizing. If one of them raises and you have not passed `return_exceptions=True`, `gather` propagates that error while the others may still be running. Those can turn into hard-to-reason-about zombie tasks unless you cancel or await them cleanly.

For finer control there is `asyncio.wait`, which is lower level. You hand it explicit Task objects and choose whether to wait for all of them, the first one to complete, or the first exception. Most application code is fine with `gather` or `TaskGroup`, and you reach for `wait` only when you need that control.

## Structured concurrency with `asyncio.TaskGroup`

Since 3.11 there is a safer, more modern option. If one child task in a group fails, the group cancels the rest, so you never leak the zombie tasks that raw `gather` can leave behind.

```python
async with asyncio.TaskGroup() as tg:
    tg.create_task(work_a())
    tg.create_task(work_b())
# by here, either all of them finished or an exception bubbled out of the group
```

For new code, prefer `TaskGroup` over a bare `gather`.

## Cancellation

`task.cancel()` schedules a cancellation. The coroutine keeps running until its next `await`, and that is where `asyncio.CancelledError` gets injected. One thing to be careful about: that error subclasses `BaseException`, not `Exception`, so a bare `except Exception` will not catch it, and you should not try to swallow it.

Use `try` and `finally` for cleanup, and if you do catch `CancelledError` on purpose, re-raise it afterward. There is also `asyncio.shield(aw)`, which protects an awaitable from being cancelled directly by a parent scope. Use it sparingly, for something like a commit you really must finish.

## Timeouts

```python
async with asyncio.timeout(30):       # available since 3.11
    await slow_operation()
```

On older versions the equivalent is `asyncio.wait_for(aw, timeout=...)`, which cancels the underlying task when the timeout fires, so keep that side effect in mind.

## Futures and awaitables

Picture ordering a latte and getting a pager. The pager is a Future. It starts out pending, you go sit down so the loop can do other work, and when the drink is ready the result gets set on the pager and it is done.

To keep the vocabulary straight: an **awaitable** is anything you can put `await` in front of, a **Future** is a low-level awaitable that stands in for an eventual result, and a **Task** is a subclass of Future that drives a coroutine to produce that result.

## `async for` and `async with`

`async for` iterates over an async iterator, like a streaming HTTP body or an async database cursor. `async with` works with an async context manager, one that defines `__aenter__` and `__aexit__`, so that setup and teardown can themselves await. That is how async connections, locks, and HTTP clients are managed.

```python
lock = asyncio.Lock()
async with lock:                  # __aenter__ and __aexit__ may await
    await mutate_shared_state()
```

## Asyncio coordination primitives

Asyncio is usually single-threaded, but the loop still switches tasks at every `await`. That means between two awaits, another task can step in and mutate shared state. The async versions of the familiar primitives exist to serialize that.

### asyncio.Lock

Serializes a critical section across `await` boundaries, so only one task is inside it at a time.

### asyncio.Semaphore

Caps concurrency. This is the canonical "scrape many URLs, but no more than five at once".

```python
sem = asyncio.Semaphore(5)
async def fetch(url):
    async with sem:               # at most 5 fetches run concurrently
        return await client.get(url)
```

### asyncio.Event

One task calls `set()` and the others sit in `await event.wait()` until it does. Good for "config loaded, now start the workers".

### asyncio.Condition

A lock combined with a condition variable, for waiting until shared state matches a predicate. You acquire the lock, check the condition, and if it is not satisfied you `await cond.wait()`, which releases the lock until a `notify` wakes you. On waking you re-acquire and check again.

### asyncio.Queue

This is the async assembly line, and it is the cleanest way to connect producers and consumers in async code.

```python
import asyncio

async def producer(q):
    for i in range(5):
        await q.put(i)            # waits if the queue is full, which is backpressure
    await q.put(None)             # sentinel

async def consumer(q, out):
    while True:
        item = await q.get()      # waits if the queue is empty
        if item is None:
            q.task_done(); break
        out.append(item * 10)
        q.task_done()

async def main():
    q = asyncio.Queue(maxsize=2)
    out = []
    await asyncio.gather(producer(q), consumer(q, out))
    print(out)                    # [0, 10, 20, 30, 40]

asyncio.run(main())
```

# Patterns and practice

## Common patterns

The **worker pool**, or bounded concurrency, is about capping how many tasks hit a resource at once. In asyncio that is a semaphore, and with executors it is the `max_workers` argument.

```python
async def scrape_all(urls):
    sem = asyncio.Semaphore(10)
    async def one(u):
        async with sem:
            return await fetch(u)
    return await asyncio.gather(*(one(u) for u in urls))
```

**Fan-out and fan-in** is splitting work across many workers and then combining the results back together. `gather`, `TaskGroup`, and `executor.map` all give you this shape.

A **pipeline** is a series of stages connected by queues. Each stage runs concurrently, and a full queue naturally applies backpressure to the stage feeding it. This scales nicely to multi-stage processing.

**Rate limiting** is worth distinguishing from concurrency. A semaphore caps how many run at the same time, but if you need a true rate, like N calls per second, you gate each call on a timer or a token bucket instead.

For CPU work, **map-reduce** means running `ProcessPoolExecutor.map` over chunks of the input and then reducing the partial results back in the parent process.

## Combining the models

These approaches compose, and the common production shape uses all three together. You let asyncio coordinate at the top for I/O, you offload blocking calls to a thread pool with `asyncio.to_thread`, and you offload CPU-heavy Python to a process pool through `run_in_executor`.

```python
loop = asyncio.get_running_loop()
# CPU-bound work without freezing the event loop:
result = await loop.run_in_executor(process_pool, heavy_compute, data)
```

## Common pitfalls

| Pitfall | Symptom | Fix |
| --- | --- | --- |
| `time.sleep()` inside a coroutine | The whole app freezes | Use `await asyncio.sleep()` |
| A blocking call like `requests` on the loop | The loop stalls under load | Use `asyncio.to_thread` or an async client |
| CPU work in threads | No speedup, thanks to the GIL | Use `ProcessPoolExecutor` |
| Forgetting `if __name__ == "__main__"` | A flood of processes on spawn | Add the guard |
| Unprotected `+=` on shared state | Lost updates and flaky bugs | Use a `Lock` or a queue |
| Acquiring locks in different orders | Deadlock | Use a consistent lock order or timeouts |
| Swallowing `CancelledError` | Tasks refuse to cancel | Re-raise it, and use `try`/`finally` |
| A bare `gather` when something fails | Zombie tasks | Use `TaskGroup` or `return_exceptions=True` |
| Sending a lambda to a process | `PicklingError` | Use top-level functions only |

## Primitive cheat sheet

| Primitive | Analogy | What it is for |
| --- | --- | --- |
| Lock | A one-person bathroom | One task or thread in the critical section |
| RLock | A key you can reuse | The same thread re-enters without deadlocking |
| Semaphore | Restaurant seating | Cap how many run at once, useful for rate limiting |
| Event | A starting pistol | Broadcast a "go" to many waiters |
| Condition | A buzzer with rules | Wait until shared state matches a predicate |
| Barrier | A group photo | Everyone waits, then all proceed together |
| Queue | A conveyor belt | Hand off work between producers and consumers |

## Choosing a tool

| Goal | Reach for |
| --- | --- |
| Many concurrent I/O operations in one process, with async libraries | `asyncio` plus async libraries |
| A blocking library you cannot replace | `asyncio.to_thread`, plain threads, or `ThreadPoolExecutor` |
| Parallel CPU-heavy Python across many cores | `multiprocessing` or `ProcessPoolExecutor` |
| Structured fan-out and fan-in with sane error handling | `TaskGroup`, on 3.11 and later |
| Passing data between workers safely | `queue.Queue` for threads, `asyncio.Queue` for async, `multiprocessing.Queue` for processes |
| Capping concurrency against a service | A semaphore, either `threading` or `asyncio` |

To wrap up: concurrency in Python is really one question with three answers. Decide first whether your work is waiting or computing. The GIL then tells you that threads can overlap waiting but not computing, and that processes can do both as long as you accept that they do not share memory. Everything else in this note, the locks and queues and the event loop, is just the machinery for coordinating whichever answer you picked.
