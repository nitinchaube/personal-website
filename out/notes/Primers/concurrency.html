Concurrency in Python

June 21, 2026·38 min read·Foundations

My complete, plain-English reference for concurrency in Python: concurrency vs parallelism, the GIL, threads, multiprocessing, concurrent.futures, asyncio, every synchronization primitive, and the patterns and pitfalls that connect them.

These are my full notes on doing concurrent work in Python. I wrote them so I would never have to open ten browser tabs again the night before an interview or a tricky bit of work. They go from the absolute basics (what concurrency even means, why the GIL exists) all the way up through threads, processes, and asyncio, and they cover every coordination primitive plus the patterns and pitfalls I actually run into.

The one idea that everything hangs off of: before I pick any tool, I ask whether my program spends most of its time waiting (network, disk, a database) or computing (loops, parsing, math in Python). Waiting points me at asyncio or threads. Computing points me at processes. Almost every detail below is downstream of that single split, and the reason the split exists at all is a thing called the GIL.

The foundations#

Concurrency vs parallelism: not the same thing#

I mix these up less now that I have a clean picture of each.

Concurrency is about dealing with many things at once. You have several jobs in flight and you keep switching between them so none of them stalls everything else. One cook running four pots, stirring whichever one needs attention, is concurrent. There may only ever be one cook.

Parallelism is about doing many things at once, literally at the same instant, on different hardware. Four cooks at four stoves is parallel.

Python can do both, but not with the same tool. Threads and asyncio give you concurrency on a single core. Multiprocessing gives you real parallelism across cores. The GIL is the reason threads give you concurrency but not parallelism, which is the whole knot I untangle next.

The four models, told as a restaurant#

The four ways of getting work done map cleanly onto a restaurant, and this is the picture I fall back on whenever I get confused.

  1. Synchronous, which is just ordinary Python. One waiter takes an order, walks it to the kitchen, and stands there until the food is ready. Nothing else happens while they wait.
  2. Threads. I hire ten waiters who share one kitchen. They take turns at the single stove, because only one of them can actually cook Python at a time, but while one waits for the oven another can keep busy. This shines when there is a lot of waiting to overlap.
  3. Asyncio. One extremely efficient waiter. They take an order, hand it to the kitchen, and immediately move to the next table. When a bell rings, meaning some I/O finished, they pop back to that table and continue. One person, almost never standing idle.
  4. Multiprocessing. I build ten separate restaurants, each with its own kitchen and staff. Now ten dishes really do cook at the same time, but the restaurants cannot share ingredients directly. Anything one sends to another has to be boxed up and shipped, which in Python means it gets pickled.

The row I care about most is preemptive vs cooperative. The OS can pause a thread literally anywhere, even halfway through a single statement, which is exactly why shared data between threads needs locks. Asyncio only ever switches at an await, so I always know the precise points where another task could slip in. That predictability is a big part of why async code is easier to reason about once it clicks.

The GIL: why Python threads cannot use all your cores#

CPython keeps its own internals consistent (mostly reference counts and object memory) using one global lock. The rule it enforces is short: only one thread runs Python bytecode at any given moment. That lock is the Global Interpreter Lock, the GIL.

What the GIL actually protects#

Every Python object carries a reference count, and the interpreter bumps that count up and down constantly as names come and go. If two threads bumped the same count at the same time without coordination, the count would drift, objects would get freed too early or never, and you would get crashes and leaks. The GIL is the cheap, blunt fix: hold one lock around all bytecode execution, and the counts can never be touched by two threads at once.

When the GIL is released#

This is the part that makes threads useful at all. A thread does not hold the GIL the entire time it runs.

  • When a thread blocks on I/O (a socket read, a file read, time.sleep), it releases the GIL so other threads can run. That is why threads overlap waiting so well.
  • Many C extensions release the GIL around heavy native work. A lot of NumPy math, hashing, compression, and database drivers drop the lock while they crunch in C, then take it back. So "CPU-heavy" work that lives in C can still parallelize across threads.
  • Even pure Python code gets interrupted. The interpreter forces a check roughly every 5 milliseconds (you can read the value with sys.getswitchinterval()) and hands the GIL to another waiting thread. So a thread can be paused between any two bytecodes, which is the root of the race conditions I cover later.

Free-threaded Python, the part that is changing#

Starting with 3.13, under PEP 703, there are experimental builds of CPython that run without the GIL and give genuine multi-core parallelism for plain Python code. You can check whether it is active:

It is opt-in today and still maturing, since some C extensions need to be updated to be safe without the lock, but it is clearly where things are heading. Until it is the default, I assume the GIL is present, which means for parallel Python compute I reach for processes.

CPU-bound vs I/O-bound: the question that decides everything#

This is the single classification I make before touching any concurrency tool.

Kind of workWhere the time goesWhat I reach for
I/O-boundWaiting on network, disk, a database, a subprocessasyncio with async libraries, or threads for blocking libraries
CPU-bound in pure PythonComputing: loops, parsing, math written in Pythonmultiprocessing or ProcessPoolExecutor
CPU-bound but inside native code that frees the GILHeavy NumPy or C-extension mathThreads or processes, either works

To tell which one I have, I look at where the time genuinely goes. If a function mostly sits inside requests.get, open().read, cursor.execute, or an await, it is I/O-bound. If it mostly grinds through for loops, string and JSON work, or math in plain Python, it is CPU-bound. When I honestly cannot tell, I profile it instead of guessing, because my intuition is wrong often enough to matter.

A rule of thumb I trust: asyncio is at its best when I spend most of my time awaiting I/O. If a function would block the thread for milliseconds or more without ever hitting an await, I keep it off the event loop and offload it, which I explain in the asyncio section.

How to choose, as a quick map#

The rest of these notes take the three toolkits one at a time, then cover the primitives and patterns that span all of them.

Threads: good for waiting, useless for crunching#

Threads share memory inside one process. They are cheap to start and they are my go-to for overlapping work that spends its time blocked on I/O. The price for that shared memory is that I have to coordinate access to anything more than one thread can touch, which is most of the difficulty.

Starting threads with the threading module#

target is the function to run and args are its arguments. .start() launches it on a fresh OS thread, and .join() blocks the caller until it finishes. There are also daemon threads (Thread(..., daemon=True)), which are background threads the program will not wait for. They get killed the instant the main program exits, so I use them only for things like a heartbeat logger, never for work that has to actually complete.

One sharp edge worth knowing: if a thread raises an exception, it does not crash your main program. The exception prints and that thread just dies quietly, which can hide bugs. This is one of several reasons I almost always use a pool instead of raw threads.

Thread pools with concurrent.futures, which is what I actually use#

Managing threads by hand gets tedious and easy to get wrong. Nearly always I want the high-level pool, which handles creating threads, reusing them, and collecting results.

submit(fn, *args) hands me a Future right away and the work starts in the background. map(fn, iterable) is the easy path when I just want every result in input order. as_completed(futures) is what I want when results trickle in and I would like to react to each one as it lands, for example to show progress. Leaving the with block calls shutdown(wait=True), so it will not return until everything is done.

Thread-local data: giving each thread its own copy#

Sometimes I want a variable that is global in spirit but private per thread, so threads do not clobber each other. threading.local() does that. Each thread sees its own independent attributes on the same object.

This is how things like per-request context or a per-thread database connection are usually done.

Race conditions: why I never trust shared state#

A line like counter += 1 looks like one indivisible step. It is not. It compiles to four separate bytecodes:

If the OS pauses a thread in the gap between the read and the write, another thread can read the same old value, do its own increment, and write back. When the first thread wakes up and writes, one of the two increments is silently gone.

Whether the loss actually shows up depends on timing and on the Python build, and that is precisely what makes these bugs miserable. The code passes in testing and then fails in production under load. So I stopped asking "is this operation atomic?" and started just protecting any shared mutable state with a lock.

What is atomic in CPython, and why I still do not lean on it#

A handful of single-bytecode operations happen to be atomic in CPython today, like list.append(x) or assigning dict[key] = value. They work without a lock because the GIL cannot be handed off in the middle of a single bytecode. I know this, and I still do not rely on it, for two reasons. First, it is a CPython implementation detail, not a language promise, and free-threaded builds change the ground under it. Second, anything that reads then writes, like += or if x not in seen: seen.add(x), is never atomic no matter how it looks. A lock costs me almost nothing and removes the whole class of doubt.

Locks and the rest of the primitives#

Lock#

A lock is the one-person bathroom. Only a single thread can hold it at a time, and anyone else who tries to acquire it waits until it is free.

I always use the with form so the lock releases even if the code inside raises. Keep the body small: hold the lock for as little work as possible, and never do I/O while holding it, or other threads pile up behind you.

RLock#

A plain Lock deadlocks if the same thread tries to acquire it twice, which happens more than you would expect when a method that holds the lock calls another method that also wants it. A reentrant lock, RLock, lets the owning thread re-acquire it and just counts the acquisitions, releasing for real only when the count hits zero.

Semaphore#

A lock lets exactly one thread through. A semaphore is the same idea but with a counter, so I can let, say, five through at once. The classic use is capping how many requests I fire at an external service so I do not get rate-limited or melt their server.

Event#

An event is a flag one thread flips while others wait for it. It is handy for a "configuration is loaded, you can start now" kind of signal that several waiters need at once.

Condition#

A condition is a lock paired with a notification channel, which is what I want for producer and consumer coordination where a consumer needs to wait until some shared state is ready. The pattern is always: acquire, check a predicate, and if it is not satisfied, wait (which releases the lock) until someone notifies you.

Barrier#

A barrier is a meeting point. Every thread waits at it until the agreed number have arrived, then they all continue together. Good for phased work where nobody should start phase two until everyone finished phase one.

Passing data with queue.Queue, which beats hand-rolled locks#

Honestly, the cleanest way to share work between threads is to not share raw variables at all and instead pass data through a queue. queue.Queue does its own locking internally, so I get safe handoff without writing a single Lock. This is the producer and consumer pattern.

Two variants come up: LifoQueue behaves like a stack, and PriorityQueue hands out the lowest item first. Whenever I find myself reaching for a shared list plus a lock, a queue is usually the better answer.

Deadlock, livelock, and starvation#

These are the three classic ways concurrent code goes wrong, and naming them helps me spot them.

A deadlock is when two threads each hold a lock the other one needs, so both wait forever.

My fixes: always acquire locks in the same global order, use acquire(timeout=...) so a thread eventually gives up, or avoid holding more than one lock at a time.

A livelock is subtler. The threads keep reacting to each other and changing state but never make real progress, like two people in a hallway who keep stepping the same way to let each other pass.

Starvation is when one thread never gets its turn, because others keep winning the contended lock or the scheduler keeps favoring them.

My best defense against all three is to keep shared mutable state to a minimum. Pass data through queues, keep critical sections tiny, and never hold a lock while doing I/O.

Processes: real parallelism, with a catch#

When the work is CPU-bound Python, threads cannot help, because of the GIL. Processes are the answer. Each one gets its own interpreter and its own GIL, so they genuinely run on different cores at the same time. The catch is that they do not share memory, so any data that crosses between them has to be pickled.

Process pools, the easy way#

The high-level pool mirrors ThreadPoolExecutor almost exactly, so moving CPU work from threads to processes is often a one-word change.

This version really does use all my cores. The exact same loop under ThreadPoolExecutor would be no faster than running it on one thread, because the prime check is pure Python compute.

Using multiprocessing directly#

If I want lower-level control, the multiprocessing module gives me Process and Pool.

The practical difference between Pool and ProcessPoolExecutor is small. Pool has been around longer and has imap/apply_async; the executor has the cleaner Future API and the same interface as the thread version. I default to the executor unless I have a reason not to.

Sharing data between processes#

Since memory is not shared, I need an explicit channel whenever processes have to exchange data.

Start methods and the main guard#

How a child process comes into being differs by platform, and it explains a footgun I have hit.

With fork, the historical default on Linux, the child is a clone of the parent's memory. That is fast, but the child inherits locks and threads in whatever state they were in, which can wedge.

With spawn, the default on Windows and on macOS since 3.8, Python starts a fresh interpreter and imports your module again. That re-import is the reason the if __name__ == "__main__": guard is required. Without it, every child re-runs your top-level code, which spawns more children, which spawn more, and you get an endless cascade of processes.

There is also forkserver, a middle ground that forks each worker from a clean server process.

Pickling: what can and cannot cross the boundary#

Everything I send to a process (the arguments, the return values, and the worker function itself) has to be picklable. That rules out lambdas, locally defined or nested functions, open file handles, and most lock objects. So I define worker functions at the top level of a module, where pickle can find them by name.

When processes are not worth it#

Processes are not free. Starting one is expensive, and every argument and result gets serialized and copied across the boundary. For tiny tasks that cost more in pickling and startup than they save in compute, a process pool can be slower than just doing the work in one process. When the per-item work is small, I batch items into chunks (chunksize= on map) so each process gets a meaningful amount of work per round trip. The rule I keep in mind: processes pay off when the compute per task clearly dwarfs the cost of shipping the data.

Asyncio: one thread, thousands of waits#

Asyncio gives me one thread running a single event loop that juggles thousands of overlapping I/O operations. It is cooperative, meaning tasks run until they hit an await and then voluntarily hand control back. Because only one task runs at a time, I do not need locks around pure CPU sections, but I still have to think about what happens around those await points, because that is exactly where another task can run.

The core idea, in one breath#

Instead of one thread per connection sitting blocked, I have one thread that, every time a task would block on I/O, sets that I/O going and switches to another task that is ready. The operating system tells the loop when each I/O finishes. So a single thread can keep ten thousand sockets in flight, because at any instant almost all of them are just waiting, and waiting is free.

async and await, and what they really do#

async def defines a coroutine function. Calling it does not run anything; it hands me back a coroutine object that is ready to be driven. await is the magic word: it means "pause me here, let the event loop run other things, and wake me when this is done." Under the hood await suspends the coroutine and yields control all the way back to the loop, and the loop resumes the coroutine later from exactly that line. That suspend-and-resume is the entire trick.

Running it: the entry point#

asyncio.run(coro) creates a loop, runs the coroutine to completion, and shuts the loop down. I use it once, at the top level of the program. I never nest asyncio.run() calls; inside async code I use await.

When I need the loop from inside async code, I use asyncio.get_running_loop(). I avoid the older get_event_loop() patterns unless I am stuck maintaining old code.

The event loop, step by step#

The event loop is the conductor. It decides what runs when, and it handles pausing and resuming. It keeps spinning around two questions: did any background I/O finish since I last looked, and what is ready to run right now?

It works in three phases:

  1. The ready queue. Coroutines that can run Python right now. The loop runs them one at a time, each until it yields.
  2. Execution. A task runs until it hits an await, at which point it yields control back to the loop. If it never awaits, it hogs the loop, which is the cardinal sin.
  3. The I/O watcher, the selector. When a task awaits a network call, the loop parks it and asks the OS to watch that socket. When data arrives, the OS tells the loop, and the loop moves the task back onto the ready queue.

The mental model that made this stick for me: the loop is single-threaded, so "concurrent" here means rapidly interleaved, not simultaneous. Nothing runs in parallel. It just never sits idle while something could be making progress.

Never block the loop#

This is the rule that, once internalized, prevents most asyncio bugs. The loop is one thread. If any task runs a blocking call without awaiting, the whole loop freezes and every other task stalls.

time.sleep is the obvious offender, but the same applies to any blocking call: requests.get, a synchronous database driver, heavy CPU loops, reading a big file with plain open. There is also await asyncio.sleep(0), which is a polite way to say "yield so other tasks get a turn" without waiting on any timer.

Offloading blocking and CPU work#

When I am stuck with a blocking library, or I have a chunk of CPU-heavy Python, I push it off the loop instead of letting it freeze everything.

asyncio.to_thread runs a blocking callable in a thread pool, which is right for blocking I/O because I/O releases the GIL. For CPU-heavy Python, threads would not help (GIL again), so I hand it to a ProcessPoolExecutor via run_in_executor. The key point: CPU-heavy Python belongs in processes, never on the asyncio thread pool.

Coroutines are sequential until you make tasks#

A coroutine driven by the loop moves through a few states. It is created when I call it (nothing has run yet), then scheduled onto the ready queue, then running as the loop executes its body, then suspended when it hits an await, then resumed when the awaited thing is ready, and finally done when it returns.

The catch that surprises people: awaiting one coroutine at a time, in a single flow, is sequential. Each one finishes before the next starts.

To get real overlap, I need tasks.

Tasks: real overlap#

Writing await my_coro() means "run this all the way to completion before my next line." To overlap work, I wrap it in a task, which the loop is free to interleave with others. A task starts running as soon as it is created.

One real gotcha: if I create a task and keep no reference to it, the garbage collector can destroy it mid-flight, and it just vanishes. So for fire-and-forget work I hold a reference until it is done.

gather: run many, wait for all#

gather wraps the coroutines in tasks, runs them concurrently, and gives me the results back in input order once they all finish. The caveat I always remember: if one of them raises and I did not pass return_exceptions=True, gather propagates that error while the others may still be running. Those can become zombie tasks unless I cancel or await them. With return_exceptions=True, exceptions come back in the results list instead of being raised, and nothing gets orphaned.

TaskGroup: structured concurrency, the modern default#

Since 3.11 there is a safer option. If one child task in the group fails, the group cancels the rest and then raises, so I never leak zombie tasks.

wait and as_completed: finer control#

When I need more than "wait for everything", there are two lower-level tools.

I reach for these when I want to act on early results, race several attempts and take the fastest, or implement a custom timeout. Most app code does fine with gather or TaskGroup.

Cancellation#

task.cancel() schedules a cancellation. The coroutine keeps running until its next await, and that is where asyncio.CancelledError gets injected. One thing to be careful about: that error subclasses BaseException, not Exception, so a bare except Exception will not catch it, and I must not try to swallow it.

I use try/finally for cleanup, and if I catch CancelledError deliberately, I re-raise it afterward. There is also asyncio.shield(aw), which protects an awaitable from being cancelled directly by a parent scope. I use it sparingly, for something like a commit I really must finish.

Timeouts#

On older versions the equivalent is asyncio.wait_for(aw, timeout=...), which cancels the underlying task when the timeout fires, so I keep that side effect in mind. Both work by cancelling, which is why clean cancellation handling (the previous section) matters.

Futures and awaitables#

Picture ordering a latte and getting a pager. The pager is a Future. It starts pending, I go sit down so the loop can do other work, and when the drink is ready the result gets set on the pager and it is done.

To keep the vocabulary straight: an awaitable is anything I can put await in front of, a Future is a low-level awaitable standing in for an eventual result, and a Task is a subclass of Future that drives a coroutine to produce that result. In day-to-day code I create tasks and rarely touch raw futures, which mostly show up when bridging callback-based libraries into async.

async for, async with, and async generators#

async for iterates an async iterator, like a streaming HTTP body or an async database cursor, where each step might await. async with works with an async context manager, one that defines __aenter__ and __aexit__, so setup and teardown can themselves await. That is how async connections, locks, and HTTP clients are managed.

An async generator is a coroutine that yields values over time, which I consume with async for. It is perfect for streaming results without buffering them all in memory.

The coordination primitives#

Asyncio is usually single-threaded, but the loop still switches tasks at every await. That means between two awaits, another task can step in and mutate shared state. The async versions of the familiar primitives exist to serialize that. They are the same concepts as the threading ones, just awaitable.

asyncio.Lock#

Serializes a critical section across await boundaries, so only one task is inside it at a time. I only need it when a critical section actually contains an await; pure synchronous code between awaits cannot be interrupted.

asyncio.Semaphore#

Caps concurrency. This is the canonical "scrape many URLs, but no more than five at once", and it is probably the async primitive I use most.

asyncio.Event#

One task calls set() and the others sit in await event.wait() until it does. Good for "config loaded, now start the workers."

asyncio.Condition#

A lock combined with a condition variable, for waiting until shared state matches a predicate. I acquire the lock, check the condition, and if it is not satisfied I await cond.wait(), which releases the lock until a notify wakes me. On waking I re-acquire and check again.

asyncio.Queue#

This is the async assembly line, and it is the cleanest way to connect producers and consumers in async code, with backpressure built in.

The mistakes I actually make#

A short list of asyncio errors I have personally shipped, so future me recognizes them:

  • Calling a coroutine and forgetting the await, so it never runs and I get a "coroutine was never awaited" warning.
  • Putting a blocking call on the loop and wondering why throughput collapsed under load.
  • Creating a task for fire-and-forget work, keeping no reference, and watching it vanish.
  • Catching CancelledError in a broad except and breaking cancellation.
  • Reaching for an asyncio.Lock when the critical section had no await in it and therefore never needed one.

When something is mysterious, asyncio.run(main(), debug=True) turns on debug mode, which warns about slow callbacks and coroutines that were never awaited.

Putting it together#

Patterns I reach for#

Bounded concurrency, the worker pool. Cap how many tasks hit a resource at once. In asyncio that is a semaphore; with executors it is max_workers.

Fan-out and fan-in. Split work across many workers, then combine the results. gather, TaskGroup, and executor.map all give this shape.

Pipeline. A series of stages connected by queues. Each stage runs concurrently, and a full queue naturally applies backpressure to the stage feeding it. This scales nicely to multi-stage processing.

Rate limiting vs concurrency. A semaphore caps how many run at the same time. If I need a true rate, like N calls per second, that is different: I gate each call on a timer or a token bucket.

Map-reduce for CPU work. Run ProcessPoolExecutor.map over chunks of the input, then reduce the partial results back in the parent process.

Mixing the three models#

These compose, and the common production shape uses all three together: asyncio coordinates I/O at the top, blocking calls get offloaded to a thread pool with asyncio.to_thread, and CPU-heavy Python gets offloaded to a process pool through run_in_executor.

Bridging threads and asyncio#

Sometimes I have an event loop running on one thread and code on another thread that needs to hand it work. asyncio.run_coroutine_threadsafe is the bridge: it schedules a coroutine on a loop running elsewhere and returns a regular concurrent.futures.Future.

The mirror image is loop.call_soon_threadsafe(fn), which schedules a plain function onto the loop from another thread. These two are the only safe ways to touch a loop from outside its own thread.

A quick glossary#

  • Concurrency: dealing with many things at once by interleaving them. Does not require multiple cores.
  • Parallelism: doing many things at once on multiple cores. Requires processes in Python today.
  • GIL: the lock that lets only one thread run Python bytecode at a time.
  • Coroutine: a function defined with async def that can suspend itself at await.
  • Event loop: the single-threaded scheduler that runs coroutines and watches I/O.
  • Task: a coroutine the loop is actively running, so it can overlap with others.
  • Future: a placeholder for a result that is not ready yet.
  • Critical section: code that touches shared state and must not be interrupted partway.
  • Backpressure: a full queue making a fast producer slow down to match a slow consumer.
  • Race condition: a bug where the outcome depends on the unpredictable timing of threads.
  • Deadlock: two parties each waiting on a resource the other holds, forever.

The whole thing really does collapse to one question with three answers. I decide first whether the work is waiting or computing. The GIL then tells me that threads can overlap waiting but not computing, and that processes can do both as long as I accept that they do not share memory. Everything else here, the locks and queues and the event loop, is just the machinery for coordinating whichever answer I picked.
